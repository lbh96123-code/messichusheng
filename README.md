# 选技助手

一个实时读屏的决策辅助工具。它盯着屏幕，认出场上摆着的技能图标，判断哪些已经被人拿走、被谁拿走，
然后在轮到你之前把每个候选技能的胜率算好，直接画在游戏画面上。

选技期间，左右十个玩家面板朝棋盘的一侧会显示竖向组合明细：基础、配合、队友、克制和合计分，
正分为绿色、负分为红色，零分与空值为中性色；底部显示英雄识别状态和已识别技能数量。
分数使用现有模型对已归属的英雄与技能直接评分，包含自身配合、模型中的队友配合与克制项；
它不是个人胜率或百分制评分，队伍级构成与配比项不分摊到个人。组合尚未选满时只评已有部分，
未知项目显示「待认」，完全没有可评分项目时显示「—」。归属纠正后随完整识别刷新，
无需等待推荐推演结束。托盘菜单「显示双方组合明细」可独立开关（默认开启），不影响技能推荐；
本次运行期间跨对局保留开关状态。F6 全局隐藏、主逻辑离开选技阶段时一起隐藏，下一局选技按开关状态恢复。

整个过程没有任何内存读取或进程注入，只有截屏和图像识别——所以它也必须承受读屏方案的全部麻烦：
画面是 3D 透视的、图标会被特效和浮窗遮住、同一个格子在不同时刻亮度能差三倍。
这个仓库的大部分工作量都花在这些麻烦上。

---

## 它要解决什么

一局对局里有 60 个格子（48 个普通技能 + 12 个大招）和 12 张英雄卡。10 名玩家轮流拿走其中 50 个。
插件需要在每一手落下后的一两秒内做完三件事：

| 问题 | 难在哪 |
|---|---|
| **这个格子里是什么技能** | 图标库有 513 个，画面是透视的，格子不是正方形 |
| **它被拿走了吗** | "变暗"是个模糊概念：反光、暗色原画、浮窗、鼠标都会让格子变暗 |
| **是谁拿走的** | 画面上没有任何一处直接写着"这一手是谁选的" |
| **下一手该选什么** | 候选 50+，每个都要推演到满编，而且要赶在玩家做决定之前算完 |

前三件是识别问题，第四件是搜索问题。这份文档主要讲前三件——因为它们是这个项目里真正难的部分。

## 结构

```
main.js        托盘 / 截屏 / 覆盖层窗口 / 全局热键 / 鼠标位置
  └─ worker.js   工作线程：帧状态机、快慢双通道、锁池与重锁、调用引擎
       ├─ recog.js   全部图像识别 + 归属层（Tracker）
       ├─ trace.js   观测轨迹：把每帧**看到了什么**记下来 / 离线回放
       ├─ v2.js      2.0 状态估计（变点检测 + 带容量指派），托盘菜单可切换，默认不启用
       ├─ census.js  周期性全面盘点 + 指派求解（对照实现）
       └─ engine_worker.js → engine/  胜率推演（多线程）
overlay.html   透明置顶画布，把推荐框画在游戏画面上
```

数据流是单向的：`截屏 → 识别 → 归属 → 局面签名 → 引擎 → 覆盖层`。
只有"有人落子"这一个事件会触发重算，这是推荐结果不抖动的前提。

两个**互相独立**的运行开关（托盘菜单 / F11 / F12）：

| 开关 | 选项 | 管什么 |
|---|---|---|
| 运行模式 | 正式 / 测试 | 只管截图和日志的详细程度，不改变任何判断 |
| 状态估计内核 | 1.x / 2.0 | 只管"被拿走了没有 / 归谁"，其余（认图、当前选人、胜率推演）两者共用 |

测试模式下两个内核并行跑，谁驱动输出由内核开关决定，另一个只在旁边算并记录分歧。
截图的 PNG 编码放在主进程——测试模式不占识别的时间，开不开它完整识别的帧数相同。

## 四个关键设计

### 1. 逐格贴框：识别准确率的大头

游戏画面是 3D 透视的，那块棋盘是个**梯形**——每一行的格子大小和位置都不一样，
固定版式算出来的框会偏 2~6 像素，并且会把格子之间的黑缝或边框裁进来。

这点偏移的代价比直觉大得多。在 15 张真实截图（540 个技能格）上实测：

| | 全库 513 个候选 | 池内 50 个候选（线上的实际条件） |
|---|---|---|
| 按版式框直接认 | 93.1% | 95.0% |
| 逐格贴框后 | 96.9% | **99.3%** |

贴框的做法：锁池时，拿这一格已经认出的图标当模板，在 ±4 像素 / 若干尺寸里搜一遍，
再在最优点附近细搜。棋盘整局不动，所以只算一次，之后每帧复用同一组偏移。

> 详见 [docs/recognition.md](docs/recognition.md)

### 2. 三态判定：跟它自己比，不跟阈值比

判断一个格子有没有被拿走，**不是**看它的绝对亮度，而是和**它自己在锁池那一刻的样子**比。
这条原则很重要，因为图标库里既有均值 16 的暗图标，也有大片纯色的亮图标，
任何绝对阈值都会在某一头出错。

判定结果是三态而不是两态：

- `N` 没变 —— 亮度还在参考的 0.6 倍以上
- `T` 被拿走 —— 同一张图去色压暗（实测某技能亮度降到 0.14 倍、饱和度 0.27→0.12）
- `O` 看不清 —— 两头都不像：半透明说明浮窗、鼠标挡住一角、转场动画

第三态是关键。看不清时**维持原判**，而不是猜一个。早期版本只有两态，
浮窗飘过就会产生一次误判，再由后续逻辑放大成一手假的落子。

### 3. 归属：靠"同时发生"而不是靠读文字

画面上没有任何地方写着"这一手是谁选的"。可用的线索只有两条，而且都不完整：

- **棋盘上某一格变暗了** —— 知道拿走了什么，不知道是谁；
- **某个玩家面板上多了一个图标** —— 知道是谁多了一件，但图标很小、可能认不准，而且玩家可以自己拖动调换位置。

所以归属是**配对**问题，不是读取问题：把"棋盘上刚变暗的格"和"面板上刚多出来的图标"配起来。
因为可以拖动，面板那边用的是"图标总数比已记账的多了几个"，而不是"第几个槽变了"。

配对不上时还有后备：按时间顺序配、按英雄卡的回合顺序填空、读面板标题里的英雄名做第二信号。
所有这些步骤和各自的门槛写在 [docs/attribution.md](docs/attribution.md)。

### 4. 快慢双通道：延迟从 4 秒压到 1 秒

完整识别一帧要 50~200ms，而引擎推演要 1~3 秒。如果串行等，玩家会感觉迟钝。

- **快通道**（每 250ms）：1/8 分辨率只看亮度，1ms 判完"有格子变暗了"，立刻通知引擎开始算下一位；
- **慢通道**：完整识别，连续两帧 + 面板配对才确认这一手。

快通道判出的落子会**并入局面**直到慢通道确认或否决。这条很要紧：早期版本里，
快通道说"拿走了"、慢通道还没确认，局面签名就会来回翻，引擎每手被打断重算 2~3 次，
前半局每手白等 1.5~2 秒。

## 实测数字

都是在真实截图和真机日志上量的，不是合成数据：

| 指标 | 数值 | 条件 |
|---|---|---|
| 技能格识别 | 572/576 = 99.3% | 16 张真实截图，逐格贴框 + 池内候选 |
| 错误的置信度 | 全部 ≤ 0.48 | 4 个错格分数 0.27~0.48，从不"自信地认错" |
| 面板图标识别 | 中位 0.94 | 贴框标定后；标定前 0.54 |
| 面板空槽误判 | 11/719 | v1.15 是 102/719 |
| 落子 → 出结果 | 中位 ~1 秒 | 6 线程；早期版本 2.7 秒 |

## 构建与运行

```bash
npm install
npm start                      # 本机跑
npm run pack                   # 打 Windows 包到 dist/
```

测试：

```bash
node test/baseline.js          # 真机成绩单(22 张真实截图)，改识别层必跑
node test/full_draft.js        # 整局 50 手模拟，改归属逻辑必跑
SEED=3 node test/full_draft.js # 换一局
node test/late_pair.js         # 9 种晚到/乱序配对场景
node test/restart.js           # 验证一手只算一次

TRACE_OUT=/tmp/t.jsonl node test/full_draft.js   # 记一条观测轨迹
node test/trace_roundtrip.js /tmp/t.jsonl        # 记录↔回放 必须逐字相同
node test/ab.js /tmp/t.jsonl                     # 1.x ↔ 2.0 同轨迹对比
```

`test/full_draft.js` 支持一批环境变量来制造恶劣条件：`DELAYS`（面板图标晚到）、
`WEAK`（图标认不准）、`DARK`（暗色原画）、`OCCL`（遮挡）、`BLIND`（连续几秒什么都看不见）、
`HEROMISS`（英雄卡漏认）。改动归属逻辑后应该把这些都跑一遍。

> 依赖真实截图的测试需要 `test/fixtures/*.png`，这些文件因为含有其他玩家的昵称和账号 ID 没有进仓库。
> 缺文件时那几个测试会跳过，其余照常。

## 已知的坑

**合成测试会骗人。** 模拟器把图标画在版式算出来的精确位置上，没有透视、没有偏移，
所以它**结构上无法复现**真机上最主要的错误来源。合成测试 20 局 796/800 的好成绩，
和真机上"1080p 下好几个技能没认出"可以同时成立。任何识别层的改动都必须在真实截图上验。

**池子本身会读错。** 面板上曾出现 0.94/0.95/0.99 的完美匹配，而那三个技能不在读出的池子里——
面板里只可能是从池子选走的技能，所以这是池子读错的铁证。错误是连锁的：
框贴不准 → 那格分数低 → 整行被判给错的英雄 → 补位步骤也救不回来。尚未修复。

**匹配这一步已经到顶。** 试过两条"更好的方法"并都被实测否掉:全局单应矩阵摆位
(97.9%，不如逐格贴框)、梯度方向直方图 + 颜色直方图(抗框歪但有天花板，且与像素相关
**零互补** —— 没有任何一格是它对、像素相关错的)。剩下 4 个错格分数全 ≤ 0.48，
系统自己知道没把握。力气应该花在流程死角和归属层上。

**归属层已经有 9 个步骤。** 每次真机出新问题就加一步，每步都有自己的门槛。
正确的做法是收口成一张证据表（每个信号产出带置信度的观测，最后一次性解指派）。
`v2.js` 就是这件事的完整实现（变点检测 + 带容量指派），在 14 局合成轨迹上技能归属
555/560 对 1.x 的 550/560、英雄打平、"认定被拿走"后撤回 0 次，剩下的 5 个错全部被置信度标了出来；
但它慢一到两帧，而且合成测试结构上测不到真机的主要错误来源，所以**还没有接管线上**。
见 [docs/design-2.0.md](docs/design-2.0.md)。
