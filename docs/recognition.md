# 识别层

从一张截图到"哪一格是什么技能、有没有被拿走"。全部代码在 `recog.js`。

---

## 1. 分辨率适配

版式是按 2560×1440 量的（`data/layout_2560x1440.json`）。其它分辨率按比例缩放；
4K 先缩到 2560 再处理——不是为了省时间，而是因为模板库就是按那个尺度做的，
在 4K 原生尺度上匹配反而更差。

宽高比不是 16:9 时（带鱼屏）只缩放不裁切，靠后面的格子粗检去兜。

---

## 2. 找棋盘

不假设棋盘在固定位置，每次都先粗检一遍：

1. 在画面中部一块区域里做 HSV 阈值，得到候选前景；
2. 闭运算补洞、开运算去噪；
3. 连通域，按面积和长宽比筛出"像格子"的矩形；
4. 把检出的矩形跟版式里的 60 个格子做最近邻配对，求出整体偏移 `(ox, oy)`（全体检出框中心偏移的中位数）。

检出格子数 ≥ 40 才认为"真的看到棋盘了"（`near`）。这个门槛的用处是：
游戏里很多画面（商店、记分板）会被粗检当成像棋盘，如果不卡这一条，
覆盖层会一直挂着"正在识别"的提示不消失。

### 检出框不当比对框（v1.21）

**检出只用来求整体偏移，每个格子的比对框按"逐行几何"算。** 以前检出一块就直接拿它的外接矩形去比对图标，
只要这块和旁边的东西连在一起，框就跟着歪。真机上见过三种：

| 连上的东西 | 分辨率 | 检出框 | 后果 |
|---|---|---|---|
| "终极技能"文字标签 | 1080p | 74×90（格子 62×62） | 那格匹配 0.01~0.12 |
| "标准技能"区左上/右上的黄色 L 形角框 | 2560（4K 缩到 2560 同样） | 格 13 / 格 18：72×78 / 84×78，中心偏 10px | 17 张开局帧里 15 / 13 张中招；09-13 那局格 18 只剩 0.14，那一行被祈求者反超，13 次拒绝锁池 |
| 行 4 大半格子被撑高 | 2560 | 高 0.91（真实 0.82~0.86） | 这几格长期只有 0.4~0.6 |

v1.10 的"最长边 > 1.3 倍不用"拦不住后两种。"每行取检出框中位数"也试过：多数格子一起被撑歪时中位数照样歪，1080p 大招行 5 格因此变成"未知"。

**现在的做法**（`detectBoard` / `boxesFor` / `calibrateGeometry`）：

- **逐行几何** `GEO[row] = {W, H, DX, DY}`：宽高相对版式格宽，DX/DY 是相对整体偏移的像素。没标定前用默认表 `ROW_WH`（真实开局帧的逐行中位数）。
- **锁池时按图标标定**：同一行的亮格（均值 ≥ 60，不含英雄卡）共用一组参数，目标 = 这几格"各自全库前 8 名里最高分"的平均，逐个参数网格搜两轮。
  不预设是谁的技能（不会朝认错的技能去贴），整行投票（个别格子认错、被遮挡带不偏）；不足 3 个亮格的行不标定，标定后平均分 < 0.55 的行不采用。
  开销：只算候选点积（0.13ms/次 vs 全库 8ms），每次锁池多约 0.9s。
- **英雄卡**：图标库没有英雄头像，没法标定，用所在行几何加固定修正（宽 +5%、高 +2.5%）。
- **锁池后冻结位置**：追踪每帧用锁池时的 `(ox, oy)` 和那套几何（`pool.align.G`），不再每帧检出。
  选完时只剩 28 格能检出，整体偏移会漂到 y+8，按本帧偏移 12 个亮格只有 2 格认得出，冻结后 12 格全对。
  几何跟着这次锁池走而不是全局变量 —— 重锁失败时沿用原池子继续追踪，框要和原池子的逐格微调对得上。
- **`dev`**：检出框和最终框差得多的格子（尺寸差 > 8% 或中心差 > 5px），只进日志（`诊断 … 弃用检出框`）和测试。

回归：`test/box_align.js`（事故帧 + 1080p 大招行 + 全部真实帧上"弃用的检出框"双向对比：最终框明显更好 164 个，检出框明显更好 26 个，平均 +0.098）。

> 这个坑最早（1080p）被误判成"图标库过时了"，09-13 又先被怀疑成"读到了插件自己的覆盖层"。真相两次都是框。
> 教训：匹配分突然很低时，先把框画出来看，别先怀疑模板。

### 黑格不参与认英雄（v1.21）

一行是哪个英雄，由三格技能的排列打分决定。**全黑的格子（已被选走，`isBlack`）对每个英雄都记 `UNK`**，
只留 1% 原分数给同一英雄内部决定这格记成哪个技能。黑格上的匹配分是噪声：09-13 那局行 4 左格 29 火焰风暴亮着 0.87，
格 30/31 全黑（亮度 14/8），以前靠黑格噪声碰巧认成孽主；框改对之后，剃刀靠同样的噪声以 0.017 反超（剃刀在亮格上只有 0.43）。

## 3. 逐格贴框

棋盘是 3D 透视的，是个梯形：每行格子的大小和位置都不同。固定版式框平均偏 2~6 像素。

实测偏移分布（2560×1440，格宽 72）：同一行内的偏移大体一致，行与行之间成系统性变化——
1080p 那张里第 0~1 行 y 偏 +2、第 2~3 行偏 −2、第 5 行为 0。这是透视，不是噪声。

**做法**（`refineBoxes`）：锁池时对每个格子，拿它已经认出的图标当模板，

```
粗搜：dx, dy ∈ {−4, 0, +4} × 尺寸 ∈ {0, +4}
细搜：在粗搜最优点附近 ±2
只有分数确实提高了才采纳；本来就 ≥ 0.85 的格子直接跳过
```

英雄卡没有模板可对，借同一行技能格偏移的中位数（同一行透视一样）。

棋盘整局不动，所以只在锁池时算一次，之后每帧照用同一组偏移。

**效果**（15 张真实截图，540 个技能格）：

| | 全库 513 候选 | 池内 50 候选 |
|---|---|---|
| 不贴框 | 93.1% | 95.0% |
| 贴框 | 96.9% | 99.3% |

贴框后剩下的 4 个错格，分数分别是 0.27 / 0.40 / 0.41 / 0.48——全部偏低。
也就是说**认错的时候一定伴随低分**，这比再抬那 0.7% 更有用。
（4 个里 1 个是已经变暗的格，3 个在翻牌动画那一帧。）

## 4. 模板匹配

- 模板库 513 个图标，预处理成 int8 量化向量 + 每个模板一个缩放系数（`lib_i8.bin` + `lib_scale.bin`）；
- 取样：格子内缩 6%，面积平均缩到固定尺寸，去均值后归一化；
- 打分：归一化相关（点积）。

**只对候选算点积**。给定候选集时（例如"池子里这 50 个"），只算这 50 个；
不限定时才扫全库。早期版本不管候选多少都先扫 513 个 × 12288 维，
光是面板 40 个槽位就是 2.5 亿次乘法，纯属白烧。

### 关于描述子分辨率的一个反直觉结果

在**没贴框**的框上（最坏情况）测了几种分辨率，全库 513 候选：

| 描述子 | 正确率 |
|---|---|
| 64×64 彩色 | 92.8% |
| 32×32 | 93.1% |
| 16×16 | 93.9% |
| 8×8 | **94.4%** |

**分辨率越低反而越准**——因为高分辨率是在跟几何误差较劲。
但这个结论只在框没贴准时成立：贴准之后，各种分辨率都收敛到同一个数字。

### 让匹配自己搜几何：试过，不划算

既然是几何误差，那让匹配器自己在一小簇形变里取最大分，是不是就容错了？试了：

| 方案 | 未贴框 | 已贴框 |
|---|---|---|
| 直接匹配 | 93.1% | 96.9% |
| 搜 27 种（位移 ±3 + 缩放） | 95.7% | 97.8% |
| 搜 81 种（再加剪切） | 95.6% | 97.8% |
| 几何与身份**联合**搜（前 8 候选 × 125 种几何） | — | 94.1% |

两个结论：

1. **贴框已经把几何问题吃干净了**，再搜形变只在没贴准时兜底；
2. **自由度给多了会更差**。联合搜掉到 94.1%，因为**分数在不同几何之间不可比**——
   框越缩越容易在平滑区域碰出高分。所以结构必须是"先在标准位置定身份，再为这个身份贴几何"，
   而不是两件事一起优化。

不过搜形变确实能把"第一名领先第二名"的中位从 0.471 抬到 0.546，低分率从 2.0% 降到 1.1%。
也就是说它**对置信度有用、对判别没用**。

### 两条"更好的方法", 都被实测否掉了

匹配对框的位置很敏感, 很自然会想:有没有办法绕过"把框摆准"这件事?试了两条, 都不成立。

**假设一:60 个格子共享同一个投影变换。**
棋盘看着像一个平面在 3D 里的投影, 那就不该逐格独立贴框(60 × 4 = 240 个自由度),
而应该用所有格子一起解出那一个单应矩阵(8 个自由度), 再用它摆放全部格子 ——
连暗格、被挡的格、认不出的格都能一起摆对。

实测:用已贴准的格子反解单应矩阵, 拟合残差中位 **4.07 像素**(格子才 72 像素宽)。
如果真是一个平面的投影, 残差该是亚像素级的。用它摆位只有 **97.9%**, 不如逐格贴框的 99.3%。
**前提不成立** —— 那些格子更像是各自摆放的 UI 元素, 不是一块刚性平面。

**假设二:换一种天生不在乎对齐和调色的表示法。**
屏幕上就是原图本身, 只是换了角度和调色。梯度方向直方图(HOG)正是为此设计的:
调色只改梯度强度、不改方向; 空间分格池化让几像素位移不影响结果。
再配一个完全不看位置的颜色直方图。

| | 未贴框·全库 | 未贴框·池内 | 已贴框·全库 | 已贴框·池内 |
|---|---|---|---|---|
| 像素相关(现在) | 93.1% | 95.0% | 96.9% | **99.3%** |
| HOG + 颜色 | **96.0%** | 96.9% | 96.2% | 97.0% |
| 三者相加 | 96.5% | 97.2% | 97.7% | 98.1% |

HOG+颜色确实**抗框歪**(框歪时 96.0% vs 93.1%), 但**有天花板**:把框贴准了它也只到 96.2%,
因为它把细节丢了。无脑相加反而更差 —— 弱的把强的拖下来。

那能不能让它当兜底, 只在像素相关没把握时出手?也不行。互补性统计:

```
两者都对 559   只有相关对 13   只有 HOG 对 0   都错 4
```

**没有任何一格是 HOG 对、像素相关错的。** 零互补 —— 任何组合的上限就是 99.3%。

**结论:对"匹配"这一步, 现在这个方法配上贴准的框已经到顶了, 匹配不再是瓶颈。**
剩下 4 个错格的分数是 0.27 / 0.38 / 0.40 / 0.41, 领先第二名 0.01~0.13,
系统自己知道没把握; 其中 3 个还在翻牌动画那一帧(插件本来就不在动画中锁池)。
后续的力气应该花在流程死角和归属层上, 不是继续优化匹配。

## 5. 三态判定

判断一格有没有被拿走，跟**它自己在锁池那一刻的样子**比，输出三态：

```
T  被拿走   同一张图去色压暗，或直接变黑
N  没变     亮度还在参考的 0.6 倍以上
O  看不清   两头都不像
```

具体规则（`cellState`）：

| 条件 | 判定 | 为什么 |
|---|---|---|
| 均值 < 10 且最亮 < 20 | T | 纯黑 |
| 参考有颜色，现在颜色没了，且没变亮 | T | **左下角那些光面反光的格子**：被拿走后是"有光泽的黑"，亮度反而比暗色原画还高（35~67 对 46），只能靠"颜色没了"认 |
| 英雄卡：近黑且低饱和 | T | 英雄卡被拿走是直接变黑 |
| 亮度比 ≥ 0.6 | N | 没变 |
| 技能格：亮度比 < 0.32 且九宫格最亮也暗 且 去色 | T | 要求**整格均匀变暗**，防止半格被挡 |
| 其余 | O | 维持原判 |

`O` 这一态是关键。半透明说明浮窗只把格子压暗到 0.62~0.9 倍而且颜色还在，
鼠标只挡一角——两者都不满足"整格均匀 + 去色"，落进 `O`，于是维持原判，不产生误判。

**鼠标位置**由主进程每帧传进来，指针所在的格子直接判 `O`。

### 防抖与回撤

- 连续 N 帧判 T 才确认；连续 6 帧判亮才撤回；
- 来回翻 3 次以上的格子标记为"闪烁"，先当没被拿走（真拿走了会一直黑，6 帧后自然认回来）；
- **已经连续暗 ≥ 12 帧的格子不再回撤**。这条治的是"鼠标悬停在已被拿走的格子上，
  提示框把它照亮，插件以为它回来了"。

## 6. 面板槽判空

面板（每个玩家一条，显示他已经选到的技能）是第二信号。判"这个槽里有没有图标"
曾经用绝对亮度门槛，这是个**错误的设计**：

空槽底板本身带渐变和高光，画面一亮（转场 / 技能特效 / 翻牌动画）就会亮到超过门槛，
于是整排空槽被当成有图标，再硬配成池子里的技能——实测 719 个真空槽里误判 102 个，
最高能配出 0.56 分。日志里"某一侧 4 个面板凭空各多 4 个图标、一口气记了 16 手、
还误判成新的一局"，根子就在这。

**现在的判据是纹理**（拉普拉斯标准差）：空底板是平的，图标有细节。

```
均值 ≥ 60          → 有图标（空槽实测最高才 45；免得大片纯色的图标被当成空的）
否则 纹理 ≥ 10     → 有图标
否则               → 空
```

门槛 10 是按**整个图标库**校准的：实测游戏里渲染出来的纹理是图库原图的 1.35~1.58 倍，
取最保守的 1.35 换算，513 个图标里最低的那个正好是 10——一个都不会漏。

效果：误判 102 → 11。剩下的 11 个集中在"技能说明浮窗盖住面板"那一种画面
（浮窗是深色底 + 白字，纹理高但很暗），由"手数不能多于棋盘暗格数 + 1"兜底。

> 试过再加饱和度条件来挡浮窗（浮窗没颜色、图标有颜色），**否决了**：
> 图库里本来就有没颜色的图标（某些技能饱和度只有 0.10~0.15），
> 饱和度门槛一加就要漏掉 24 个以上真图标。不能为了挡浮窗去赌颜色。

**更正确的做法**是把棋盘那条原则搬过来：锁池那一刻面板槽必然全空，
把每个槽自己的空样子记下来，之后"有图标"= 和它自己的空样子不一样了。
没有魔法常数，整体明暗变化自动免疫。这是下一步要做的。

## 7. 面板槽贴框标定

技能槽的框和真实图标差一两像素、而且普遍偏小。面板是平的 UI，同一侧所有槽偏移一样，
所以标定一次用一整局：拿这一侧已经认出的、分数最高的 5 个槽，
在位移 ±4 / 尺寸 −4~+12 里找**总分**最高的一组（先粗后细）。

只用 5 个槽、而且每个只跟它自己那一件比——全部槽 × 全部候选要 7 秒，这样 0.2 秒。

效果：面板匹配分中位 **0.54 → 0.94**。

尺寸范围原来只能往大调（0~+6），实测真实最优常在 +8，够不着；现在两头都放开。

## 8. 读池子：用"同一英雄三个技能"的结构约束

`readPool` 不是逐格独立认的。棋盘上每一行的同一侧是**同一个英雄的三个技能**，
所以按行分组求解：对每个英雄，枚举它的三个技能在这三格里的全部摆法，取总分最高的组合；
再按行的得分从高到低分配英雄（每个英雄只能用一次）。

这个结构约束很值钱：单格分数 0.33 的格子，靠同行另外两格 0.9 的分数就能定下来。

大招格单独处理：先按分数配对，剩下的按排除法配给还没分到大招的英雄——
即使分数低到 0.05，只要不明显更像别的图标，也照配。
（曾有一局三个大招格分数都 < 0.25 没配上，结果技能被拿走时引擎不知道那是什么。）

最后一步是**以图标为准的补位核对**：技能不足的英雄会由别的英雄的技能补位，
所以每格再拿全库最像的图标核一次——占位的未知格分数 ≥ 0.55 就认；
已经配上的格要全库最像的明显更好（高出 0.2 且本身 ≥ 0.6）才改判。

### 这里有个未修的问题

面板上曾出现三个 0.94 / 0.95 / 0.99 的完美匹配，而那三个技能**不在读出的池子里**。
面板里只可能是从池子选走的技能，所以这是池子读错的铁证。

错误是连锁的：某格框贴不准 → 分数低 → 整行被判给错的英雄 → 补位那一步因为
分数没过门槛也救不回来。

面板其实是个免费的纠错信号，而且比棋盘可靠得多（标定后中位 0.94，那几个错格只有 0.3~0.5）。
应该加一步：面板某格全库匹配 ≥ 0.85 且不在池子里 → 这技能确实在这局，
回棋盘上找那个低分格改正。尚未实现。

## 补位改判必须领先它自己的第二名（09-12 真机事故）

读池子最后一步是"以图标为准"：某一格全库最像的那张图标，如果明显好过行约束给出的答案，就改判成它。
这一步是必要的——技能不足 3 个的英雄会由别人的技能补位，大招区也会有空位。

但它原来只看两件事：分数够不够高（≥0.6）、比行内答案高多少（≥0.2）。
**没有看它在全库里领先第二名多少**，于是"根本没认出来"的格子也能触发改判：
认不出的时候，全库前几名总是挤在一起。

09-12 两台机器打同一局，同一格贴框收敛到不同结果：

| | 框 | 结果 |
|---|---|---|
| x 机 | 72×62 | 超负荷 0.84（行约束，未改判） |
| y 机 | 84×78（把边框裁了进来） | **真空 0.73（改判）**，全库第二 液态冰霜 0.642，**领先只有 0.088** |

后果是两人的池子不同 → 引擎局面不同 → **两人从头到尾看到的推荐都不一样**。

真机 14 次改判实测分得很开：

| 类型 | 全库领先第二名 |
|---|---|
| 合法补位（原本是"未知"格） | 0.408 ~ 0.590 |
| 覆盖 OMG 变体（正确） | 0.207 / 0.293 |
| **五次错误改判** | **0.012 ~ 0.088** |

门槛取 **0.15**，只卡"覆盖行约束"这一支（原本就是未知格的补位没有竞争对手，不受约束）。
22 张真机截图上另有两处跟着改对，判据很硬——修后的答案都是**这一行自己英雄的技能**：

- 巫医那一行：恶魔敕令（拉席克的，不在池子里）→ 麻痹药剂（巫医的）
- 帕格纳那一行：致盲之光（光之守卫的，不在池子里）→ 幽冥守卫（帕格纳的）

## 9. 本人座位（v1.22）

插件要知道"我"是十个座位里的哪一个：单人模式只给我出推荐，胜率按我方视角算，个人权重只作用于我的回合。

### 以前为什么会认错

游戏给**本人的面板**画一圈亮绿线，最清楚的是**英雄头像那一侧**的竖边（左边面板在左边、右边面板在右边）。
v1.21 以前量的是面板上下两条边 + 技能那一侧的竖边的平均颜色（"绿度" = G − max(R, B)），要求 > 25 才更新。
头像那一侧被故意排除（怕头像颜色干扰），而绿线恰恰在那一侧：

- 10 个面板的绿度实测最高只有 6~11，**门槛从来没过过**；
- 过不了门槛时就拿**锁池第一帧"最绿"的面板**当自己，并且整局沿用；
- 2560（4K 缩到 2560 同样）碰巧常对：同一台机器 21 张截图全对、4K 16 张对 15 张；
- 1080p 每次都落到**右 2**：09-14 朋友那局坐右 5，整局推荐都算给了右 2；09-11 两局也对不上截图里的真实座位。

界面上看不出任何异常（状态行照常写"我 R2"），这也是一直没被发现的原因。

### 现在怎么量（`rimScore` / `readPanels().selfRim`）

头像那一侧的面板边缘，左右各 6px（按比例）的每一列，数有多少比例的行是亮绿（G > 100 且比 R、B 都高 50 以上），取最高三列的平均：

| | 分数 |
|---|---|
| 本人（85 张真实截图，1080p / 2560 / 4K / 半分辨率） | 0.49 ~ 0.82 |
| 本人，且正轮到自己选（10 张） | 0.49 ~ 0.82（绿框不会被高亮盖住） |
| 非本人最高（绿头发的琼英碧灵头像） | 0.29 |
| 翻牌动画、选完转场 | 全部 0 |

本人是一条**贴边、上下连续**的竖线（每列约八成的行是绿的，离开边缘立刻掉到一两成）；
绿色系头像是一片**散开**的绿，没有贴边的陡边——所以量"比例最高的几列"而不是"一片区域里有多少绿像素"。
是比例，和分辨率无关，不用按分辨率换门槛。

### 怎么决定（`Tracker.updateMe`）

- **每次完整识别投一票**：只有一个面板 ≥ 0.42、且比第二名高 ≥ 0.25 才投给它，否则弃权。
- **最近 6 次里同一座位 ≥ 3 票、别的座位都不到 2 票** → 认定（或改判），日志记 `[me] 认出本人座位 R5` / `[me] 本人座位改判 …`。
- **认定之前"我" = 空**：不猜、不出推荐，状态行写"还没认出你是几号位"。锁池那一帧也投一票，通常锁池后 2~3 次识别就认出。
- 翻牌、转场看不到绿框的帧弃权，已认定的座位不变；单帧别处出现绿框不改。
- **托盘「我是几号位」手动指定**永远优先，只对指定时的这一局有效；换了一局 worker 通知主进程把菜单改回"自动"。
- 轨迹里每个面板记 `r`（绿框分数），回放和线上看到同一个数；老轨迹没有这个字段，回放时"我" = 空。

回归：`test/me_seat.js`（真实截图 + 投票逻辑 + 真 worker 合成局）；真机基准 `test/baseline.js` 每帧记 `me` / `meRim`。

> 教训：状态里有一个"从来不说不知道"的量（锁池第一帧硬猜并整局沿用），错了就是静默地错。
> 宁可显示"还没认出"，也不要拿猜的结果去算。
