新开一局就要重启：定位到跨局隐藏原生窗口的回归

结论与置信边界

已确认一个每局都会触发的代码问题：上一局结束进入 idle 时，主进程调用 overlay.hide()；新一局开始再调用 showInactive()。这违反了项目此前保留的“透明窗口常驻、只清空内容”的显示策略。原代码注释明确记载过：隐藏后重新显示可能无法回到独占全屏游戏上方。

你在 23:22 重启之前，程序已恢复选技状态，并有 60 行推荐、无画布错误。因此，这次“看不到”主要指向窗口显示层，而不是一直没识别到新局或一直没算出推荐。跨局 hide/show 是目前证据最强的原因，已经修复；Windows 实际层级丢失仍未在本机直接复现。

这段逻辑由 dd5fe7a（v1.48.5，2026-10-15 11:23，北京时间）引入，早于我们的 PR #2。此前报告没有确定重启问题的归因；本次新增的是代码历史与跨局时间线证据。

为何每新开一局都可能重现

isVisible() 只报告窗口的显示状态；advicePainted 只报告渲染代码完成推荐绘制。两者都不能证明覆盖层实际在游戏上方。原有自动恢复主要检查进程、心跳和画布错误，因此遇到“窗口还活着、内容也画了、只是看不见”的情况，不会自动重建。

历史差异中，dd5fe7a 将空闲处理由“显示原生窗、发送 clear”改成了“hide、开启后台节流、发送 clear”，并把置顶维护与健康检查都限定为需要显示时运行。常驻窗口的说明仍保留在代码里，实际实现却已经相反。

其他假设的核对

假设本次判断
上一局生命周期卡住，无法识别新局不能解释这次 23:22 的故障：重启前已经 active、有 60 行推荐。其他局面下的识别失败不因此被全部排除。
GPU 不可用，推荐始终未完成不能解释这次故障：重启前已有推荐。此前 GPU0 预热成功，GPU1 的失败是另一设备探测；第一局池子为 12/36/11 导致算法回退也不是窗口不可见的直接证据。
渲染进程崩溃或画布绘制异常上述重启前的报告没有画布错误，仍有绘制和心跳，缺少支持该假设的证据。
遮挡导致启动时短暂读不到棋盘新进程 23:22:42 截图有资源管理器遮挡，确实能造成识别延迟；不能解释重启前已经成功生成并绘制推荐后仍看不见。

本次修改

  1. 原生覆盖窗常驻：启动页面加载完成即显示透明窗口；局间空闲、暂停、F6 隐藏和捕获等待均不再调用原生 hide()，避免反复撤销与重建显示层级。
  2. 显式控制内容：主进程通过 presentation 消息控制绘制。关闭内容时立即清空 canvas、状态文字和提示；迟到的旧 state/advice 也不能把它们画回来。F6 的两秒提示保留，结束后清空。
  3. 保留健康检查：不再对透明覆盖窗开启后台节流；空闲和隐藏期间也处理无响应、心跳超时和画布错误，避免旧分数卡卡在实战画面上。
  4. 日志区分两种显示：overlay-visibility.visible 记录内容开关，新增 nativeVisible 记录原生窗状态；渲染健康记录新增 presentationVisible。它们仍不是最终屏幕可见性的证明。

本次没有调整“何时判定选技结束”的视觉规则，也没有修改推荐模型。进入游戏后分数卡何时隐藏，仍依赖现有游戏阶段确认；本修复保证收到隐藏指令后能清空内容。

还需要的真机确认与当前兜底

在 Windows 上连续玩两局、不退出插件，确认第二局直接显示；中间再执行一次 F6 隐藏/恢复，以及一次切出/切回游戏。核对新日志：空闲时应为 visible=false, nativeVisible=true；新局应为两者均 true，随后有推荐绘制回报。还应观察透明窗口常驻后的空闲 CPU / GPU 占用，本机尚未测量 Windows 实际资源变化。

如果推荐已经产生、仍看不见，可使用现有托盘入口 “悬浮窗卡住了? 点这里重建”。该入口只重建覆盖窗口，识别线程和当前池子继续保留。它和 F10 的“恢复本局（保留池子）”不同：前者处理窗口，后者处理选技状态。健康但层级异常仍可能需要这个人工入口；本次未声称自动检测到所有 Windows 显示异常。
