# 性能与延迟

## v1.49.4 新增诊断（2026-10-22）

针对同型号5060 Ti的端到端耗时差异，新增以下证据。它们可以缩小瓶颈范围，不保证仅凭日志就能区分驱动与硬件问题。以下历史章节中的旧引擎耗时和结果展示规则不作为当前duel模式的定义。

| 记录 | 内容与口径 |
|---|---|
| `machine-performance-info` | CPU型号、逻辑线程、内存、系统与Node/Electron版本，修订号20261022 |
| `gpu-telemetry` | 选技活动期间每15秒异步读取NVIDIA全卡占用、频率、温度、功耗、显存；包括游戏和其他程序，不能当成插件独占用量；记录查询起点及查询耗时 |
| `fixed-input-benchmark` | 复用启动预热原有5次固定输入测速，记录每次耗时、首跑、模型指纹、精度与批大小；`inferenceRunsMs`排除日志钩子，`runsMs`保留旧选卡计时口径。启动测速只描述当时状态，不替代游戏中的持续对照 |
| `native-start` / `native-end` | 每秒抽取调用边界，慢于250ms的完成调用也保留；新推理计时从调用运行库到await返回，单调高精度时钟，排除前后同步诊断钩子，包含运行库、驱动、传输、系统调度与JS恢复等待，不能称为纯GPU执行时间 |
| `job-performance` | 任务号、手数、分配设置；每次成功推理的分桶计数（上界1/2/4/8/16/32/64/128/250ms及以上，互斥分桶），任务期间日志写盘耗时与条数；CPU时间是整个进程，包含其他Node线程；事件循环样本来自计算线程，20ms分辨率，不能把正常约20ms采样间隔解读成20ms额外停顿 |
| `search-profile` | 根候选、编码、网络调用、先验整理、模拟落子与续选、回传及其余墙钟时间；各项不重叠。根候选本身包含编码与网络调用，不能再与任务原生推理时间相加 |

`job-performance`的非推理时间是墙钟残差，包含处理、调度和诊断，不等同于CPU执行时间。初始化已从该残差扣除；进程CPU与日志统计则覆盖整个任务（含初始化）。诊断写盘时间不包括当前摘要及后续job-end自身。原生计时口径标记`timingSchema:2`，不能直接与旧版整数毫秒、含日志钩子的计时混算。

机器及GPU记录写在`diag_main_*.jsonl`，任务/测速/推理记录写在`diag_combo_*.jsonl`，沿用现有上传选择和文件轮转。主进程日志容量可能使早期硬件记录被轮转；分析时应一起保留`.previous.jsonl`。采样只读，不更改功耗、频率、驱动或计算设置；缺失字段为空。NVIDIA在Windows WDDM下部分信息不可用，见[NVIDIA官方nvidia-smi文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。遥测以15秒采样，不能排除采样间隔内的短时抢占或降频。

拿到新日志后，先按模型指纹、批大小、精度、运行库、分配设置分组，再看推理分桶与显卡状态、编码/模拟时间、调度等待、日志写盘是否共同增加。同机同输入且分别在游戏开/关时复测，才能进一步隔离游戏负载；不要直接用不同玩家的全局均值推断显卡优劣。

---

目标：**上一个人选完 → 推荐结果出现**，尽量压到 1 秒以内，并且中途不抖动。

## 延迟由什么构成

| 段 | 耗时 | 说明 |
|---|---|---|
| 发现有人落子 | ~250ms | 快通道扫描周期 |
| 完整识别一帧 | 50~200ms | 取决于分辨率和需不需要重新标定 |
| 确认这一手 | 1~2 秒 | 连续两帧 + 面板配对 |
| 引擎推演 | 1~3 秒 | 候选数 × 线程数 |

早期版本这些是**串行**的，中位延迟 2.7 秒（开局 3~4 秒，后期约 1 秒）。

---

## 快慢双通道

**快通道**（每 250ms）：把画面缩到 1/8 分辨率，只比较亮度。
判断"有格子变暗了"只要 1ms。一旦发现，立刻通知引擎开始算下一位——
不等慢通道确认。

**慢通道**：完整识别。画面签名没变时整帧跳过（`skipped`）。

### 快通道的落子要并入局面

这是一条踩过坑才加上的规则。

快通道说"这一格拿走了"，慢通道要 1~2 秒才确认。这段时间里，如果局面签名
把这一手时有时无地翻来覆去，引擎每次都要从头重算。真机日志实测：
**一手之内重算了 3 次**，落子后 0.4 秒和 1.7 秒各打断一次，前半局每手白等 1.5~2 秒。

现在的做法：快通道判定的落子直接并入局面，直到——

- 慢通道确认它（正式记账），或
- 看到它又亮回来（否决），或
- 超过 6 秒还没确认（放弃）。

效果：`test/restart.js` 验证一手从重算 3 次降到 1 次。

---

## 只在"有人落子"时重算

推荐结果抖动的根源是重算触发得太随便。现在的规则：

- 局面签名 = 已拿走的技能集合 + 当前该谁选。**只有这个签名变了才重算**；
- 随机数种子固定，同样的局面永远给同样的结果；
- 引擎结果**只发完整的**，不发中间态；
- 上家一落子就锁定，一个回合内最多换一次推荐。

---

## 引擎

推演每个候选到满编、取平均，这一步在 6 线程上约 1.6 秒 + 精修 0.8 秒（57 个候选）。
单线程要 7.3 秒 + 3.6 秒。

线程池常驻，不每次重建。

还没做的优化：

- **逐次减半**：先给所有候选少量样本，淘汰明显差的，再把样本集中到前几名。
  预计省 ~0.8 秒；
- 精修样本数从 512 降到 256：能省时间，但推演本身分辨不了 1 个百分点以内的差别，
  降样本会让前几名的排序变成抽签——**不建议**。

## 一帧里都干了什么

```
每 250ms  快通道：1/8 分辨率扫亮度 → 有变暗？→ 通知引擎开始算
每一帧    画面签名比对 → 没变就跳过
          完整识别：贴框 → 三态判定 → 防抖 → 归属
每 200 帧 面板槽贴框重新标定（需要面板上至少有 3 个图标）
落子事件  局面签名变化 → 引擎重算 → 覆盖层重画
```
