同局不同分数，至少存在三种不同条件

结论

“大家用了相同模型、相同评分条件”在这局并不成立：一个客户端运行 1.48.5 + 自然经济分配，另外两个运行 1.49.0 + 双方最优经济分配。仓库对应版本的评分资源有变化；仅切换经济分配口径也足以改变分数卡。

这局末尾的三份识别阵容完全相同，都是 10 个英雄、40 个技能。固定模型版本和口径后，十个座位的重算分数一致；按日志中的版本和口径重算，9 个座位在两位小数的显示上不同。选技中还存在短暂输入不同：一个客户端已经配上技能，另一个还没配上。

目前没有在这些对照中复现“相同输入、相同模型、相同口径，评分器仍算出不同值”。这不等于排除了所有现场显示问题，具体证据边界见末节。

同样的方法还抽查了约 21:54 开始的一局，C02/C03/C05 末尾十人阵容在统一新版模型和最优口径下重算一致。此补充检查不代表昨天所有对局、所有时段都已验证。

三：推荐顺位不是这张分数卡的简单排序

推荐要针对哪一个座位、现在选还是提前预估、还隔几手、哪些候选可选、用哪档搜索以及计算到哪一步求结果。即使裁判模型相同，这些条件不同，技能顺位也可以不同。

这局中的差别为什么不能要求顺位一致
C01 是 mcts，C02/C03 是 duelCPU 现役推演与双方搜索的选择策略、推演过程不同；同一终局评分模型不能保证得出相同推荐。
C01 预估右四、C02 预估右二、C03 给右一当前回合计算座位已有技能、轮到他的时间和中间的选取不同；不是相同决策点。
C02 开局日志标“网络档”，C03 很快有 duel 阶段结果输出所处的预估／当前回合与计算阶段不同。日志表明 C02 配置仍为 duel，不能将当时的临时输出与另一端完整搜索结果视为同算法、同进度。
中途某端暂时漏配技能搜索输入及可选集合可能不同，候选打分和顺位随之改变。

本次没有在相同决策点、相同输入、同档位和同预算下重新运行 Windows GPU 搜索，因此不宣称已经排除推荐搜索自身的差异或其他排序问题。这里能够确认的是：原始跨客户端日志里，以上可比条件并未统一。

怎样让分数更容易比较

  1. 先统一安装版本及评分资源。仅看“都是这个插件”不够；应有同一个构建版本，最好同时核对模型指纹。
  2. 将“显示 → 团队分配”统一为相同开关状态。开启是双方最优经济分配，关闭是双方自然经济分配。两者都合法，但分数含义不同。
  3. 比较分数卡时同时核对英雄、技能数和完整十人阵容。技能刚选下时允许短暂识别差；持续不一致再查具体漏配或错配。
  4. 若产品上要求所有人看到固定、可直接对照的组合分，可以让分数卡固定一个公共口径，并把搜索的经济假设单独保留；否则应在卡片或状态区明确标出当前评分口径。
  5. 后续诊断宜记录模型指纹、评分口径及十人输入哈希。这样同一分数争议能直接判断是模型、参数、输入还是显示层不同。

本次完成的是定位、重算工具和回归检查；没有更改玩家设置、模型权重或评分规则。是否固定公共口径属于产品选择，不能通过这次核对擅自替用户统一偏好。

一致性回归通过：同版本／口径／阵容跨客户端一致、重复调用一致、输入顺序变化无可见差异、份额模式只改变该分项，以及现有三种布局测试。夹具保留本局匿名最终阵容与版本／口径，不需要外部日志即可重算；历史权重从本地 Git 提交读取。

不能超出证据的部分：日志没有保存每次实际渲染的玩家分数卡，也没有客户端已安装评分资源的完整哈希。因此表中的数值是仓库对应版本重算值，不能冒充现场截图值；也不能凭版本号逐字确认每台电脑实际加载的所有资源。尤其 C01 可能包含本地构建改动，需要未来的模型指纹才能彻底消除这个不确定性。

同版本下份额开关的差异已单独控制重现；相同输入的确定性也经过验证。未复现同条件数值漂移，不能据此保证所有显示缓存、旧版本组合、GPU 搜索预算或其他对局都不存在问题。
