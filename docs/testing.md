## 两套测试，各有各的盲区

### 合成测试：`test/full_draft.js`

自己画出一整局的每一帧，模拟 50 手，最后核对"每个技能归属给谁"。
支持一批环境变量制造恶劣条件：

| 变量 | 制造什么 |
|---|---|
| `SEED` | 换一局（固定随机数，可复现） |
| `DELAYS` | 面板图标晚到 |
| `WEAK` | 图标认不准 |
| `DARK` | 暗色原画 |
| `OCCL` | 遮挡 |
| `BLIND` | 连续几秒什么都看不见 |
| `HEROMISS` | 英雄卡漏认 |
| `NAMES` | 英雄名信号开关 |

改归属逻辑必须跑这个，而且要跑多个种子。

### 合成测试会骗人

模拟器把图标**画在版式算出来的精确位置上**，没有透视、没有偏移、没有梯形。
所以它**结构上无法复现真机上最主要的错误来源**。

这不是假设，是实测过的：合成测试 20 局 796/800 的成绩，
和真机上"1080p 下好几个技能没认出"同时成立，两者不矛盾——它们测的根本不是同一件事。

同样地，"面板空槽被当成有图标"那个 bug（真机上一帧误判 30 个槽）在合成测试里
**一次都不会出现**，因为模拟器画的空槽是干净的纯黑。

**结论：识别层的任何改动都必须在真实截图上验，合成测试只能证伪不能证明。**

### 真机基准：`test/baseline.js`

24 张真机截图（v1.21 起含 `reject_brood_2560_0913` / `bracket_2560_0912` 两张棋盘对齐事故帧）跑成一张**成绩单**，和上一次的成绩单逐项对照，有变化就列出来。
没有人工标注，所以判据全部取"结构上必然成立"的那一种：

| 判据 | 为什么它不需要标注 |
|---|---|
| 池子：12 个英雄、行裕度、未知 / 补位 / 救回的格数 | 线上 `tryLock` 的接受条件就是前两项 |
| **池外高分** | 面板里只可能出现池子里的技能——出现了池外的高分匹配，就是**池子读错的铁证** |
| **计数等式** | 面板里有图标的槽数 应 = 棋盘上"看着已被选走"的技能格数（17 张可锁帧里 13 张精确相等） |
| 面板匹配分分布、认名率 | 逐帧对照上一次 |
| 三态：同一局两帧互为参考 | 见下 |

```bash
node test/baseline.js            # 跑一遍并与 test/baseline.json 对照(有变化 exit 1)
node test/baseline.js --accept   # 确认无误后存成新基准
node test/baseline.js --only xxx # 只跑名字含 xxx 的帧
```

**谁和谁是同一局，也是结构性判出来的**，不靠文件名也不靠人工标注：拿 A 的池子去看 B，
那些判"没变"的格子应该还是同一张图标；同一局吻合率很高，不同局立刻塌掉。

### 观测轨迹与回放：`trace.js` / `test/trace_roundtrip.js` / `test/ab.js`

1.x 的日志里只有**结论**（某技能归了谁、某格撤销了），没有**观测**。
所以真机打过的对局没法回放，"新版本在真实数据上不劣于旧版本"根本无法验收。

`trace.js` 把追踪层真正从画面里读的四样东西写成 JSONL：棋盘每格的亮度统计、面板每槽的均值与纹理、
面板某槽对池子每件技能的匹配分（int16）、面板标题英雄名的匹配分。记的是**原始量**不是判断结果，
所以换一条判据时不用重跑像素。

```bash
TRACE_OUT=/tmp/t.jsonl SEED=3 node test/full_draft.js   # 合成局 + 记轨迹(顺带写 .expect.json)
node test/trace_roundtrip.js /tmp/t.jsonl               # 记录↔回放 等价性
node test/ab.js /tmp/t.jsonl ...                        # 1.x ↔ 2.0 同轨迹对比
```

**`trace_roundtrip.js` 的验收标准是逐字相同**：同一局，读像素得出的归属和日志，
必须和纯从轨迹回放（完全不碰像素）得出的一模一样，且观测缺口为 0。
这条标准很严，也正因为严才有用——达到它踩了四个坑，每一个都会让"回放"悄悄变成另一件事：

- 分数行用 int8（1/127 ≈ 0.008）→ 阈值边上翻判。换 int16。
- 记录时用未量化的原值、回放用量化值 → 两边看到的不是同一个数。
- 懒加载补算的分数行没标成"这一帧新算的" → 落盘写成"接着上一行"，回放沿用了过期的行。
- 英雄名缓存没检查是否覆盖本次全部候选 → 少一个候选，排序后的第一名就可能不一样。

代价 4.2 KB/帧（一局约 1 MB），**回放比线上快 600 倍**（1.3ms/帧 vs 100~200ms/帧）。
`worker.js` 真机上默认开启，写在日志目录，跟日志一起 7 天后清理；单局上限 40 MB。

### 真机上的对比:测试模式

`test/worker_trace.js` 把 `worker.js` 当成真的工作线程跑起来（合成帧当截屏），验证
**真机那条路**能自动锁池、开出观测轨迹、且轨迹可回放。四种开关组合都要跑：

```bash
AD_TEST=0 AD_CORE=1x node test/worker_trace.js    # 正式 + 1.x(和以前完全一样)
AD_TEST=1 AD_CORE=1x node test/worker_trace.js    # 测试 + 1.x
AD_TEST=0 AD_CORE=v2 node test/worker_trace.js    # 正式 + 2.0
AD_TEST=1 AD_CORE=v2 node test/worker_trace.js    # 测试 + 2.0(两版并行 + 记分歧)
```

**一条硬指标:开不开测试模式，完整识别的帧数必须相同。** 否则测试模式就在干扰它自己要测的东西——
第一版就栽在这里：PNG 编码放在工作线程，27 帧只来得及做 21 次完整识别。
把编码挪到主进程之后，25 / 25、24 / 24 完全一致。

> 真实截图含有其他玩家的昵称和账号 ID，没有进仓库。缺文件时相关测试跳过。

## 一个方法论教训：标准答案从哪来

早期量"识别准确率"时，我拿**读出来的池子**当标准答案，去评判逐格匹配的对错。
这是循环论证：池子是**带结构约束**（同一行三格属同一英雄）解出来的，
逐格匹配是**无约束**的，两者本来就该不一样。用前者评判后者，
量到的是"约束带来的增益"，不是"准确率"。

而且这样量出来的 93% 也不是线上的真实水平——线上认面板图标时候选只有池子里的 50 个，
不是全库 513 个。换成正确条件重测，同一批数据是 99.3%。

**教训：先确认标准答案是独立的，再谈准确率。** 在没有独立标注时，
优先找"结构上必然成立"的判据（例如：面板里只可能出现池子里的技能——
出现了池子外的高分匹配，就是池子读错的铁证）。

## 改动前后必做的事

1. `node test/baseline.js` —— 真机成绩单必须零变化（或每一处变化都能解释）；
2. 跑 `full_draft.js` 至少 5 个种子，**和改动前的版本 A/B 对比**；
3. 动了识别层或观测源：`bash` 跑一遍 11 种条件的 `trace_roundtrip`，必须全部"逐字相同、缺口 0"；
4. 动了归属层：`node test/ab.js` 跑整个轨迹语料；
5. 记下数字，别只看"通过"。

> 这不是形式主义。这次改"面板判空"时，第一版规则在真实截图上表现很好，
> 但合成测试从 39/40 掉到 37/40——是 A/B 对比才发现的。
> 原因是新规则会漏掉图库里最暗的那几个图标。
> 如果只看"真实截图上误判少了"，就会带着一个新 bug 发版。
