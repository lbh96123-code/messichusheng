第一项：保留真正的末轮，不取消正常结束

旧条件 pickedCount ≥ 50 → clear 会在暗格或英雄多计时提前清空。现在检查十人的完整合法阵容：十个不同英雄、四十个不同已知技能、每人四技能且恰有一个大招。缺英雄、未知占位、重复技能或本人未选满均不靠总数 50 判定完成。

test/oct15_turn_advice.js 运行实际 worker 调度，替换昂贵的推荐计算：真实末轮输入继续请求推荐；构造的合法完整阵容触发清空。这两项同时通过，连选手次的 72 个组合也通过。

第二项：持续多计的原因

追踪器对同一格连续暗满 12 次后，直接永久返回“已选”，不会再累计亮帧撤销。这个保护原本用于避免已选卡片被鼠标重新照亮后误撤销；但它同时作用于从未在任何玩家面板中确认的技能。随后 pickedKeys() 又把这些长期未配对的暗格加入已选集合，pickedCount() 将其与英雄一起计数，超过 50 后触发推荐复核。

长时间暗格 → stable + darkRun ≥ 12
          → 无面板归属，也被永久锁为已选
          → 实际观测恢复为 N（亮），累计状态仍为 T（已选）
          → 多计 → 超过 50 → 推荐暂停

这条永久锁定逻辑在仓库可见的最早提交 5a14ef9 中已经存在，属于旧问题。具体何种遮挡或画面变化造成最初误判，不能仅凭观测轨迹确定。

修复约束

  • 只对没有玩家面板配对的技能放开长期锁定；仍需累计 6 次清晰的 N 观测才撤销。
  • 前 5 次亮观测继续视为不可选，并请求完整观测，避免短暂亮回就推荐出去；O（看不清）不作为撤销证据，新的 T 会重置亮观测计数。

第三项：分数卡与推荐共用显示条件

状态推荐与分数卡

收到 clear一起隐藏；后续仅到达评分 state 不能单独把卡片画回来。

恢复识别等新推荐到达，再一起出现。
空闲阶段收到迟到推荐，或重建覆盖窗渲染器与重放缓存都拒收空闲阶段的迟到结果，避免带到下一局。
F6、暂停、进入游戏、捕获等待服从共同显示开关；“显示玩家分数”设置仍允许单独关闭分数卡。

本次没有再加新的结束判定。即使游戏 HUD 的确认迟到，只要推荐已经因为策略阶段、完整阵容或 clear 而隐藏，分数卡也随之隐藏。
